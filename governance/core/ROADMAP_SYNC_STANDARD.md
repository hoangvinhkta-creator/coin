# Roadmap Sync Standard

## Purpose
Keep one technical roadmap as the source of truth while automatically generating a second Markdown roadmap that a non-programmer can read.

Canonical source:
`PROJECT/PROJECT_PROGRESS.md`

Generated human-readable view:
`PROJECT/LO_TRINH_DE_HIEU.md`

The generated file is NOT an independent roadmap and MUST NOT be edited by hand.

## Canonical Roadmap Table

Inside `PROJECT/PROJECT_PROGRESS.md`, the `## Overall Roadmap` section MUST contain one Markdown table with exactly these machine-readable columns:

| Status | Task ID | Tên việc | Mục đích | Tier | Effort | Thứ tự/phụ thuộc |
|---|---|---|---|---|---|---|

Rules:
- `Task ID` is the canonical identifier and must be unique.
- `Tên việc` is the canonical task name used by both roadmaps.
- `Mục đích` explains business/user purpose in plain Vietnamese.
- `Status` uses the task lifecycle values from `CLAUDE.md`.
- `Tier` uses `A`, `B`, `C`, `D`, or `DUYET` for a human approval gate.
- `Effort` uses `low`, `medium`, `high`, `xhigh`, `max`, or `-` for `DUYET`.
- `Thứ tự/phụ thuộc` must name relevant Task IDs/Gates when practical.

For every MAJOR implementation task, Tier and Effort MUST be calculated independently by the deterministic router in `AGENT_CAPABILITY_MATRIX.md`. Do not derive Effort from Tier and do not manually choose Tier/Effort without routing evidence.

Routing evidence (`D/R/B/A/X`, `U/V/H/C/F`, categories, model score, effort score, applied floors, warnings) is MANDATORY in the task definition/current-task metadata for MAJOR tasks. The canonical roadmap table stores the calculated result for display; it is not the source of the routing calculation.

Before roadmap sync, run `validate_routing.py`. A Tier/Effort value that does not match the deterministic router is invalid. The generated easy roadmap is derived from the validated canonical result plus the model mapping in `AGENT_CAPABILITY_MATRIX.md`.

## Generated Easy Roadmap

`PROJECT/LO_TRINH_DE_HIEU.md` MUST be generated by:

```bash
python governance/scripts/governance/sync_easy_roadmap.py
```

Its main table MUST have exactly these five columns:

| Tick | Tên việc | Mục đích | Mức xử lý | Thứ tự/phụ thuộc |
|---|---|---|---|---|

`Tên việc` is generated as `TASK-ID — Tên việc` so the technical and non-technical views always share the same identifier and name.

`Mức xử lý` is generated as:

`<Tier> — <Model class> — <Effort>`

Examples:
- `A — Haiku — low`
- `B — Sonnet — medium`
- `C — Opus — xhigh`
- `D — Fable — max`
- `Duyệt — Con người — -`

## Tick Mapping

- `DONE` → `✅`
- `READY`, `IN_PROGRESS`, `IMPLEMENTED`, `VERIFYING`, `BLOCKED` → `🟡`
- `NOT_PLANNED`, `PLANNED`, `DEFERRED`, `CANCELLED` → `⬜`

The textual status remains authoritative in `PROJECT_PROGRESS.md`. The tick is only a simplified view.

## Automatic Synchronization Rule

Any workflow that creates or modifies the canonical roadmap MUST run the sync script in the same session before completion.

This includes:
- S000 initial roadmap creation,
- S002 / Roadmap Finalization,
- task status changes,
- task rename,
- task insertion/removal,
- task split/merge,
- dependency changes,
- Tier or Effort changes,
- roadmap change proposals after approval.

Agents MUST NOT manually toggle ticks in `LO_TRINH_DE_HIEU.md`.

## Validation Rule

Run:

```bash
python governance/scripts/governance/validate_routing.py
python governance/scripts/governance/validate_easy_roadmap.py
```

The validator regenerates the expected content in memory and fails if `LO_TRINH_DE_HIEU.md` is missing or stale.

A session that changed `PROJECT_PROGRESS.md` MUST NOT be reported complete while this validator fails.

## Source-of-Truth Rule

If the two files disagree:
1. Do not repair `PROJECT_PROGRESS.md` from the easy roadmap.
2. Re-run the generator from `PROJECT_PROGRESS.md`.
3. If the source table itself is wrong, correct it through normal roadmap change control, then regenerate.
